# 화면 설계에 쓰는 지식

디자인실이 화면을 짤 때 꺼내 쓰는 지식 모음이다. 사람이 손으로 화면을 만지고 눈으로 화면을 읽는 방식에 대해 이미 연구되고 검증된 것들이다.

**점검표가 아니다.** 여기 적힌 것을 "지켰는지" 확인하지 않는다. 이 지식은 "이 게임의 플레이어에게 무엇이 낫고 왜 그런가"를 따질 때 근거로 쓴다.
서로 부딪치는 지식도 있다(세계 안에 녹이면 몰입은 늘지만 찾기는 어려워진다). 어느 쪽을 택할지는 게임이 정한다.

출처 표시: ✓ = 이 문서를 만들 때 출처를 다시 확인함. 표시 없음 = 널리 알려진 내용이지만 이 문서를 만들 때 원문을 다시 확인하지는 않음(수치를 인용할 때는 확인할 것).

## 1. 손 — 어떻게 쥐고 어디에 닿는가

| 지식 | 화면에 주는 뜻 |
| --- | --- |
| **사람들이 폰을 쥐는 법** ✓ Hoober(2013), 거리·대중교통에서 1,333명 관찰: 한 손 49%, 한 손으로 받치고 다른 손으로 누름 36%, 두 손 15%. 쥐는 법은 상황에 따라 계속 바뀐다 | 어느 한 가지 쥐는 법만 가정하지 않는다. 세로 화면에서 가장 자주 누르는 것은 화면 아래 절반, 가로 화면에서는 양쪽 아래 구석이 편하다 |
| **엄지로 누를 수 있는 크기** ✓ Parhi·Karlson·Bederson(2006, MobileHCI): 한 손 엄지 기준, 한 번 누르는 대상은 9.2mm, 연달아 누르는 대상은 9.6mm 이상이면 정확도와 선호가 떨어지지 않는다. 플랫폼 지침도 비슷하다(Apple 44pt, Android 48dp) | 540px 폭 화면(약 65mm 폭 폰)에서 9.2mm는 약 76px이다. 누르는 것은 그보다 작게 만들지 않는다. 연달아 빠르게 누르는 것은 더 크게 |
| **피츠의 법칙** Fitts(1954): 대상에 닿는 시간은 대상이 멀수록, 작을수록 길어진다 | 급할 때 누르는 것은 크고 손가락 가까이에. 화면 가장자리와 구석은 "무한히 큰" 대상이 아니다(터치에는 마우스처럼 멈춰 주는 벽이 없다) |
| **손가락이 가린다** Vogel·Baudisch(2007, "Shift"): 손가락은 누르는 대상과 그 아래를 가리고, 작은 대상일수록 무엇을 눌렀는지 알 수 없다 | 끌어서 옮기는 것은 손가락 위쪽에 보이게 띄운다. 누르는 순간 봐야 하는 정보를 누르는 자리 바로 밑에 두지 않는다 |
| **직접 조작** Shneiderman(1983): 대상을 직접 만지고 결과가 즉시, 되돌릴 수 있게 보이면 배우기 쉽고 통제감이 크다 | 가능하면 버튼으로 명령하지 말고 대상을 만지게 한다. 다만 정밀함이 필요하거나 대상이 작으면 버튼이 낫다 |

## 2. 눈 — 무엇이 먼저 보이고 무엇을 놓치는가

| 지식 | 화면에 주는 뜻 |
| --- | --- |
| **주의 없이도 튀는 것** Treisman·Gelade(1980)의 특징 통합 이론: 색, 크기, 방향, 움직임 같은 한 가지 특징의 차이는 찾지 않아도 눈에 들어온다. 두 특징의 조합(붉고 둥근 것)은 하나씩 찾아야 한다 | 가장 중요한 것 하나에 한 가지 특징을 독점시킨다(화면에서 그것만 움직인다, 그것만 그 색이다). 여러 가지를 다 튀게 하면 아무것도 튀지 않는다 |
| **보고 있어도 못 본다** Simons·Chabris(1999)의 부주의 맹시, 변화 맹시 연구: 다른 일에 집중하면 눈앞의 뚜렷한 변화도 놓친다 | 플레이어가 보고 있는 곳(주인공, 손가락 근처) 밖에서 일어나는 중요한 일은 놓친다. 상태가 바뀌었다는 신호는 시선이 있는 곳에서 주거나 움직임으로 끌어온다 |
| **주변 시야** 사람의 눈은 중심 몇 도만 선명하다. 주변 시야는 움직임과 밝기 변화에는 민감하고 글자와 세부에는 약하다 | 화면 구석의 계기는 읽으려면 시선을 옮겨야 한다. 구석에는 "달라지면 알 수 있는 것"(차오름, 깜빡임, 색 변화)을 두고, 읽어야 하는 것은 시선 가까이에 |
| **게슈탈트 원리**(가까움, 닮음, 닫힘, 이어짐, 전경과 배경): 가까이 있는 것, 닮은 것은 한 묶음으로 보인다 | 한 묶음이어야 하는 것은 붙이고 닮게, 다른 것은 떨어뜨리고 다르게. 선과 상자를 그리기 전에 간격으로 묶는다 |
| **실루엣으로 읽기** ✓ Mitchell·Francke·Eng(2007, "Illustrative Rendering in Team Fortress 2"): 어떤 조명에서도 한눈에 누구인지 읽히도록 윤곽, 밝기와 색의 차이를 설계했다 | 대상의 종류는 색보다 먼저 윤곽으로 갈라야 한다. 작게 줄이거나 검게 칠해도 무엇인지 알 수 있는가 |
| **색각** 남성의 약 8%는 붉은색과 초록색을 구분하기 어렵다 | 위험과 안전, 내 편과 적을 색만으로 가르지 않는다. 모양, 무늬, 위치, 움직임을 겹친다 |

## 3. 머리 — 얼마나 담을 수 있고 어떻게 배우는가

| 지식 | 화면에 주는 뜻 |
| --- | --- |
| **작업 기억은 작다** Miller(1956)의 "7±2", Cowan(2001)의 약 4덩이: 한 번에 붙들 수 있는 것은 몇 개뿐이다 | 화면이 기억해 줄 수 있는 것을 플레이어에게 외우게 하지 않는다. 한 번의 판단에 견줘야 하는 것이 네댓 개를 넘으면 묶거나 줄이거나 화면이 대신 계산해 준다 |
| **힉의 법칙** Hick(1952): 고를 것이 많을수록 고르는 시간이 길어진다 | 급한 순간의 선택지는 적게. 느긋한 순간(판과 판 사이)에는 많아도 된다 |
| **인지 부하** Sweller(1988): 과제 자체의 어려움과, 표현 방식 때문에 생기는 쓸데없는 어려움을 구분한다 | 게임의 어려움은 판단에서 와야지 화면을 읽는 데서 오면 안 된다. 기호의 뜻을 떠올리고 범례를 찾는 것은 쓸데없는 부하다 |
| **행동 유도와 기표** Norman(『디자인과 인간 심리』): 할 수 있는 일이 모양에서 보여야 한다. 누를 수 있는 것은 누를 수 있게 생겨야 한다 | 만질 수 있는 것과 없는 것이 생김새에서 갈려야 한다. 설명 글이 필요하다면 모양이 말하지 못하고 있는 것이다 |
| **게임 UX의 세 기둥** Hodent(2017, 『The Gamer's Brain』): 지각·주의·기억의 한계를 전제로, 기호와 반응(signs & feedback), 명료함, 형태는 기능을 따른다, 일관성, 최소 작업 부하, 실수 방지와 복구 | 플레이어가 무엇을 할 수 있는지, 방금 무슨 일이 일어났는지, 왜 그랬는지를 화면이 늘 알려 주는가. 배움은 설명서가 아니라 해 보는 과정에 넣는다 |
| **몰입(flow)** Csikszentmihalyi; Chen(2007, "Flow in Games"): 도전과 실력이 맞을 때 몰입한다. 화면이 방해하면 깨진다 | 판단하는 흐름을 끊는 것(확인 창, 화면 전환, 읽어야 하는 글)을 핵심 순간에서 뺀다 |

## 4. 게임 화면에 고유한 것

| 지식 | 화면에 주는 뜻 |
| --- | --- |
| **화면 요소의 네 종류** ✓ Fagerholt·Lorentzon(2009, "Beyond the HUD", Chalmers 석사 논문): 세계 안에 있는가(허구)와 세계의 공간에 놓였는가(기하)의 두 축으로 — 세계 밖의 평면 표시(non-diegetic, 흔한 HUD), 세계 안의 물건(diegetic, 손목의 계기), 세계 공간에 떠 있지만 세계의 것은 아닌 표시(spatial, 발밑의 원), 세계의 것이지만 화면에 붙는 표시(meta, 화면에 튄 피) | 정보를 꼭 구석의 숫자로 줄 필요가 없다. 대상 위에, 바닥에, 대상의 모습 그 자체로 줄 수 있다. 세계 안에 녹이면 몰입이 늘고 구석을 볼 일이 줄지만, 정확한 값이 필요할 때는 읽기 어려워진다 |
| **손맛(game feel)** Swink(2008, 『Game Feel』): 입력에 대한 즉각 반응(약 0.1초 안), 움직임의 가속과 관성, 충돌의 반응, 꾸밈(흔들림, 소리, 입자)이 "만지는 느낌"을 만든다 | 누르는 순간 무언가 바로 달라져야 한다. 결과가 늦게 나오는 행동이라도 "받았다"는 반응은 즉시 |
| **과장된 반응(juice)** Jonasson·Purho(2012, "Juice It or Lose It" 강연): 같은 규칙의 게임이 튕김, 흔들림, 입자, 소리만 더해도 전혀 다른 게임처럼 느껴진다 | 핵심 행동 하나에 반응을 몰아 준다. 다만 반응이 정보를 가리면(흔들림 때문에 다음 위험이 안 보이면) 해롭다 |
| **화면은 판단의 순서를 따른다** Schell(『The Art of Game Design』)의 인터페이스 렌즈: 인터페이스는 플레이어와 세계 사이의 통로이고, 가장 좋은 것은 느껴지지 않는 것이다 | 플레이어가 판단하는 순서(무엇을 보고 → 무엇을 견주고 → 무엇을 누르는가)대로 눈과 손이 움직이게 놓는다 |
| **한 화면의 일과 화면의 수** 정해진 답이 없다. 한눈에 전부를 읽어야 하는 게임(판 전체가 곧 문제인 퍼즐, 편성 전체가 곧 엔진인 게임)이 있고, 한 번에 한 곳만 보여야 하는 게임(탐험, 잠입, 조작이 바쁜 게임)이 있다 | 무엇을 한 화면에 올릴지는 "지금 내리는 판단에 무엇을 견줘야 하는가"로 정한다. 견줘야 하는 것은 같은 화면에, 견주지 않는 것은 다른 곳에 |

## 5. 모바일 — 폰에서 하는 게임이라서 달라지는 것

| 지식 | 화면에 주는 뜻 |
| --- | --- |
| **화면 자리마다 손가락의 정확도가 다르다** ✓ Hoober(2017, "Design for Fingers, Touch, and People"): 누르는 정확도는 화면 가운데에서 약 7mm, 가장자리에서 약 9mm, 구석에서 약 12mm. 그리고 사람들은 고를 수 있으면 **화면 가운데를 누르려 한다**(내용을 가운데로 끌어다 놓고 누른다) | "엄지는 아래쪽"만 알고 있으면 반만 아는 것이다. 가운데가 가장 정확하고 가장 선호된다. 구석과 가장자리에 두는 단추는 가운데보다 크게(구석은 12mm ≈ 100px/540폭 기준). 정밀하게 골라야 하는 것은 가운데에 |
| **게임 단추의 크기(플랫폼 지침)** ✓ Apple의 게임 디자인 지침: 기본 44×44pt, 덜 중요한 것은 28pt까지 줄일 수 있지만 플레이에 집중한 상태에서는 정확히 누르기 어렵다. 터치 화면은 PC·콘솔보다 큰 단추가 필요하다 | 플레이 중에 누르는 것은 44pt(540폭 기준 약 70~76px) 아래로 내리지 않는다. 28pt는 플레이가 멈춘 화면의 덜 중요한 것에만 |
| **튜토리얼은 복잡한 게임에서만 듣는다** ✓ Andersen 외(2012, CHI, 4만 5천 명 이상): 튜토리얼은 가장 복잡한 게임에서 플레이 시간을 최대 29% 늘렸지만, 단순한 두 게임에서는 유의한 효과가 없었다. 해 보며 알아낼 수 있는 규칙에는 튜토리얼 투자가 정당화되지 않을 수 있다 | 규칙이 해 보면 드러나는 게임이면 설명을 만들지 말고, 첫 판을 "한 번 누르면 규칙이 드러나게" 짠다. 설명이 필요한 것은 관습과 다르거나 복잡한 부분뿐이다 |
| **숨은 제스처는 발견되지 않는다** ✓ Nielsen Norman Group(Norman·Nielsen, 제스처 인터페이스 비판; 숨은 메뉴 연구): 눈에 보이는 단서 없는 제스처(길게 누르기, 옆으로 밀기)는 있는지조차 모른다. 숨긴 메뉴는 과제 완수를 떨어뜨린다 | 핵심 조작을 길게 누르기·두 손가락·가장자리 밀기에만 걸지 않는다. 쓸 거면 모양이나 움직임으로 "끌 수 있다, 더 있다"를 보여 준다. 단추를 없애고 직접 조작으로 가는 것과 부딪친다 — 직접 만지는 대상이 만질 수 있게 생겼을 때만 성립한다 |
| **짧게, 자주, 끊기며 한다** ✓ GameAnalytics 벤치마크(2025, 약 1만 1,600개 게임): 세션 길이 중앙값은 5~6분 안팎(상위 25%는 8~9분), 설치 다음 날 다시 오는 비율의 중앙값은 22%(상위 25%는 iOS 31~33%, Android 25~27%) | 열에 여덟은 다음 날 돌아오지 않는다. 첫 화면에서 바로 만질 수 있어야 하고, 첫 1~2분 안에 그 게임의 핵심 순간이 나와야 한다. 한 판이나 한 토막이 5분 안에 매듭지어지고, 언제 끊겨도(전화, 알림, 내릴 정거장) 잃는 것이 없어야 한다 |
| **안전 영역** 위쪽의 카메라 구멍·노치, 아래쪽의 홈 막대, 둥근 모서리에는 중요한 것이나 누르는 것을 둘 수 없다. 화면 맨 아래에서 위로 미는 동작은 시스템이 가져간다 | 맨 아래 가장자리에서 시작하는 밀기를 조작으로 쓰지 않는다. 계기와 단추는 가장자리에서 안쪽으로 물린다 |
| **소리를 끄고 하는 사람이 많다** ✓ 조사마다 수치가 크게 엇갈린다(소리를 켠다는 응답이 60~73%인 조사도, 끈다는 응답이 90%를 넘는 조사도 있다). 확실한 것은 적지 않은 사람이 소리 없이 한다는 것이다 | 소리로만 주는 신호는 없는 것으로 친다. 중요한 것은 반드시 화면으로도 |
| **밖에서 한다** 햇빛, 흔들리는 차 안, 한 손에 손잡이. 대비가 낮은 것과 작은 것은 안 보이고, 정밀한 조작은 실패한다 | 판단에 쓰는 것은 대비를 크게(글자는 배경과 4.5:1 이상), 얇은 선과 옅은 색에 뜻을 싣지 않는다 |
| **폰은 다른 일을 하다 여는 것이다** 한 손은 다른 것을 들고 있고, 눈은 자주 화면 밖으로 간다 | 세로 화면은 한 손으로 다 되게. 잠깐 눈을 뗐다 돌아와도 "지금 무슨 상황이고 내 차례인지"가 바로 읽히게 |

화면비(요즘 폰은 19.5:9~20:9로 길쭉하다)와 기기별 해상도는 여기서 다루지 않는다. 출시용으로 내보낼 때 정할 일이다. 설계는 게임의 기준 크기(세로 540×960 / 가로 960×540)로 한다.

## 쓰는 법

- 화면을 정할 때 "왜 이렇게 했는가"의 근거로 쓴다. 제안서에는 실제로 판단을 가른 지식만 적는다(전부 나열하지 않는다).
- 지식끼리 부딪치면 이 게임에서 무엇이 더 중요한지로 고르고, 무엇을 포기했는지 적는다.
- 여기 없는 지식을 써도 된다. 출처를 댈 수 있으면 댄다. 지어낸 출처는 쓰지 않는다.
- 이 문서에 보탤 것이 생기면 보탠다(대표의 결재 메모에서 되풀이되는 지적, 플레이테스트에서 확인된 것).
