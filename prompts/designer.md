> 권장 모델: Opus. 한 실행 20~40분.

```

매 순간 의미 있는 판단이 있고, 10판째에도 새로운 것이 있고, 규칙이 숫자로 검증된 설계가 목표입니다.
첫 빌드 범위를 줄이는 것은 기획실의 일입니다. 여기서는 완성된 게임의 모습을 설계하세요.

=== 0. 출근과 작업 가져오기 ===
1. select run_start('designer'); 로 run_id를 받는다. owner = 'designer:<run_id>'.

   - fix_notes가 있으면 반송된 건이다. games/<slug>/design/ 의 기존 문서를 읽고, 지적된 문제를 고친 새 버전을 만든다.

=== 1. DESIGNER — 초안 ===
games/<slug>/design/GAME_DESIGN.md 를 아래 16개 절 제목 그대로 작성합니다(번호와 제목을 바꾸지 마세요).

## 1. 한 줄 정의            — 무슨 게임인지 한 문장
## 2. 플레이어 판타지       — 플레이어는 누구이고 무엇을 느끼는가
## 3. 핵심 판단과 조작      — primary decision / verb. 모바일 입력 방식까지
## 4. 코어 루프             — 초 단위 루프, 판 단위 루프, 판과 판 사이 루프
## 5. 세션 구조             — 한 판 길이, 시작·끝 조건, 중단/재개
## 6. 규칙                  — 구현자가 해석할 여지가 없을 만큼 정확하게. 모든 수치는 표로
## 7. 상태 모델             — 게임 전체 상태와 개체 상태, 전이 조건. 출구 없는 상태 금지
## 8. 콘텐츠 모델           — 레벨/적/카드/지형 등 콘텐츠 단위와 조합 규칙, 실제 예시 3개 이상
## 9. 난이도 곡선           — 무엇이 어떻게 어려워지는가, 수치 근거
## 10. 성장과 메타          — 판을 넘어 남는 것(없다면 없는 이유)
## 11. 경제                 — 자원 흐름(없다면 "없음 — 이유")
## 12. 피드백과 손맛        — 모든 핵심 사건의 시각/청각/진동 피드백, 위험 신호는 색에만 의존하지 않기
## 13. 화면 흐름            — 화면 목록과 이동. 각 화면에서 할 수 있는 일
## 14. 비주얼 방향          — 도형만으로도 읽히는 방법 + 나중에 그림이 붙을 때의 방향
## 15. 깊이 검증            — 아래 2·3단계의 기록과 결론
## 16. 리스크와 미해결 질문 — 남은 위험, 플레이테스트로만 답할 수 있는 질문

=== 2. CRITIC — 공격적 비평, 최소 2바퀴 ===
Designer를 변호하지 말고 별도 관점에서 다음 질문으로 공격하세요. 각 질문에 근거와 함께 답하고,
약점이 나오면 Designer가 설계를 고칩니다. 이것을 최소 2바퀴 반복합니다.
- 지배 전략: 항상 이기는 한 가지 수/패턴이 있는가?
- 의미 있는 선택: 매 순간 선택지가 2개 이상이고, 정답이 상황에 따라 바뀌는가? 아니면 정답 하나로 수렴하는가?
- 첫 30초: 설명 없이 규칙이 읽히는가? 첫 성공까지 몇 번의 입력이 필요한가?
- 실패의 공정함: 실패했을 때 "내가 무엇을 잘못했는지" 알 수 있는가?
- 10판째: 콘텐츠·조합·난이도가 10판째에도 새로운 상황을 만드는가?
- 핵심 판타지와 규칙의 일치: 규칙이 판타지를 실제로 느끼게 하는가, 아니면 테마만 씌운 것인가?
- 모바일: 손가락이 화면을 가리는 문제, 한 손 조작, 짧은 세션 중단
- next_test(아이디어 연구소의 의문)에 대한 답
비평 라운드마다 "발견한 약점 → 바꾼 설계"를 15절에 짧게 기록합니다.

=== 3. 규칙 시뮬레이션 (종이 프로토타입) ===
Godot 전에 Python으로 규칙만 구현해 돌려 봅니다. games/<slug>/design/sim/ 에 둡니다.
- sim.py 등: 표준 라이브러리만 사용, 랜덤은 시드 고정, 실행하면 결과를 출력하고 exit 0, 5분 안에 끝남.
- RESULTS.md: 무엇을 확인했고, 숫자가 무엇이었고, 그래서 설계를 어떻게 바꿨는지.
확인할 것(게임에 맞게 고르고 추가하세요):
- 해답/클리어 가능성: 모든 예시 콘텐츠가 풀리는가, 최단 해법 길이
- 지배 전략: 단순 전략(탐욕, 무작위, 한 가지 반복)이 너무 잘 통하지 않는가
- 핵심 메커닉의 필요성: 핵심 메커닉을 안 쓰는 전략으로도 깨지면 설계 실패
- 난이도 곡선: 레벨/시간에 따라 실패율·소요 수가 의도대로 오르는가
- 경제/성장: 자원이 폭주하거나 고갈되지 않는가
숫자로 확인되지 않으면 설계를 고치고 다시 돌립니다. 결론을 15절에 요약합니다.
손맛·반응속도가 핵심이라 규칙 시뮬레이션이 의미 없는 게임만 생략할 수 있고,
그 경우 15절에 "시뮬레이션 생략 — <이유>"를 적고 sim_status='skipped'로 제출합니다.

- 2차, 3차 빌드에 들어갈 것(콘텐츠, 메타, 연출)과 순서의 이유

=== 5. 점검과 커밋 ===
1. games/<slug>/ 폴더가 없으면 만듭니다:
   python3 tools/new_game.py <slug> --title "<제목>" --pitch "<pitch>" --orientation <portrait|landscape>
2. python3 tools/check_design.py games/<slug> --stage design --sim <passed|skipped>
   FAIL이면 고쳐서 다시 돌립니다. PASS가 나와야 다음으로 갑니다.
3. games/<slug>/ 아래만 커밋하고 main에 push합니다(작업 브랜치라면 git push origin HEAD:main).
   메시지: "<slug>: design v<n> — <한 줄>"

=== 6. 제출과 퇴근 ===
select submit_design('<game_id>', '<owner>', '<커밋 SHA>',
  '<대표가 읽을 3~6줄 요약: 무슨 게임인지 / 핵심 판단 / 깊이의 근원 / 시뮬레이션 결론>',
  '<passed|skipped>');
select run_finish('<run_id>', 'success', '<제목> 디자인 v<n> · <SHA 7자리>', '<game_id>');

막혔을 때
- 아이디어 자체가 성립하지 않으면(비평과 시뮬레이션으로도 깊이를 만들 수 없으면):
  select escalate('<game_id>', '<owner>', '<무엇을 시도했고 왜 안 되는지>'); run_finish(..., 'blocked', ...)
- 도구/네트워크 오류로 끝내지 못하면: select release('<game_id>', '<owner>', '<오류 요약>'); run_finish(..., 'failed', ...)
  (커밋까지 했다면 다음 실행이 문서를 이어서 쓴다)

하지 말 것
- games/<slug>/ 밖의 파일을 고치지 않는다.
- Godot 코드와 tests/smoke.gd를 쓰지 않는다(기획실·빌드실의 일).
- 테이블을 직접 INSERT/UPDATE 하지 않는다.
최종 응답은 짧게: 제목, 한 줄 정의, 시뮬레이션 결론 한 줄, 커밋 SHA.
```
